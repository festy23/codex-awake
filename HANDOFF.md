# Handoff codex-awake

Состояние на 28 октября 2026 года. Репозиторий: [festy23/codex-awake](https://github.com/festy23/codex-awake).

Цель следующего этапа — превратить подтверждённую доставку события в исходный чат Codex Desktop в небольшую локальную утилиту: Rust backend, очередь effectum в файловой SQLite и прямой вызов App Server через локальный TCP WebSocket. Пробуждение неактивного чата проверено живым тестом. Production backend, интеграция effectum и наблюдение произвольного уже запущенного процесса ещё не реализованы.

Это передача контекста и результатов исследования, а не замена формальных спецификаций. Начинай с [AGENTS.md](AGENTS.md), [индекса модулей](docs/modules/index.md) и спецификации изменяемого модуля. Решения пользователя из этого handoff не переоткрывай без новой причины; незавершённые контракты не заполняй собственными defaults.

## 1. Задача и границы первой версии

Пользователь заранее поручает Codex продолжить работу после завершения конкретного процесса. Пока процесс работает, модель не вызывается. После события утилита доставляет сообщение в тот же чат с ранее разрешённой инструкцией продолжения.

Первый сценарий:

1. Зарегистрировать наблюдение за **уже запущенным локальным процессом** и сохранить исходный чат и инструкцию продолжения.
2. Дождаться завершения процесса средствами ОС, без опроса состояния моделью.
3. Обработать событие через устойчивую очередь.
4. Передать сообщение в исходный чат; результат команды агент проверяет по инструкции пользователя.

Факт завершения не означает успех команды. Получение exit code, stdout и stderr, запуск или перезапуск наблюдаемой команды не входят в первый сценарий. Начальная платформа — macOS. TeamCity, другие CI, Linux и Windows относятся к дальнейшим этапам; их контракты ещё не выбраны.

## 2. Утверждённые решения

| Область | Решение |
|---|---|
| Программа | Локальный backend на Rust |
| Очередь | Встроенная Rust-библиотека effectum |
| Хранение очереди | Файловая SQLite; не in-memory база |
| API Codex | App Server JSON-RPC, `thread/queue/add` |
| Транспорт | Локальный TCP WebSocket на loopback-адресе |
| Адресат | App Server, обслуживающий исходный чат Desktop |
| Совместный доступ | Desktop и backend — два клиента одного общего App Server |
| Ожидание | Без вызовов модели и расходования токенов на проверки |

Rust + effectum + SQLite утверждены 27 октября; WebSocket — 28 октября 2026 года. NATS JetStream и JetStream KV заменены этим решением. PostgreSQL, pg-boss и Pueue в выбранную архитектуру не входят.

Версия effectum, физическая схема прикладного состояния, параметры worker и гарантии восстановления пока не закреплены. SQLite — механизм хранения, а effectum — очередь задач; выбор SQLite сам по себе не обеспечивает доставку события в Codex.

## 3. Целевая связка

```text
Уже запущенный процесс
        │ событие завершения
        ▼
Rust backend → effectum / файловая SQLite → обработчик доставки
                                                   │
                                      локальный TCP WebSocket
                                                   │
                                                   ▼
Codex Desktop ───────── WebSocket ─────────► общий App Server
                                                   │
                                           thread/queue/add
                                                   │
                                      очередь исходного чата
                                                   │
                                        новый ход при idle
```

Backend не запускает отдельного inference-агента вместо Desktop. Отдельный App Server для записи в общее хранилище Codex не используется. Существующий приватный сервер Desktop нельзя сделать общедоступным только открытием соединения из Rust: сервер должен уже принимать подключения на общем endpoint.

Постоянное WebSocket-соединение backend не требуется для выбранного сценария. Доставка может состоять из подключения, handshake, проверки адресата, одного запроса и отключения. Полный production-контракт соединений и таймаутов остаётся частью S3.

## 4. Что выяснено об App Server

Исследован локально официальный [openai/codex](https://github.com/openai/codex) на коммите [`f021168bde5357009fceb0477835ad90bd54c17c`](https://github.com/openai/codex/commit/f021168bde5357009fceb0477835ad90bd54c17c). Это исследовательский snapshot `main`, а не версия бинарника, использованного в живом тесте.

- `stdio://` — один клиент, JSONL через stdin/stdout. В обычном исследованном запуске этим каналом владел Desktop.
- `ws://IP:PORT` — WebSocket listener с несколькими клиентами.
- `unix://` и `unix://PATH` — Unix-сокет, внутри которого тоже выполняется WebSocket handshake и передаются WebSocket frames.
- В исследованном запуске выбирается один локальный транспорт. Флага для дополнительного локального listener поверх работающего stdio-сервера не найдено.
- Обычного HTTP POST для `thread/queue/add` нет. TCP listener обслуживает HTTP health probes и WebSocket Upgrade.
- `thread/queue/add` — экспериментальный RPC; клиент включает `experimentalApi: true` при `initialize`.
- `clientUserMessageId` служит корреляции; дедупликация повторных вызовов этим полем не подтверждена.

При добавлении через сервер, который держит нужный чат загруженным, очередь сохраняет сообщение и непосредственно вызывает `wake_if_loaded`. Затем idle lifecycle обрабатывает очередь и вызывает `start_turn_if_idle`. Этот путь не ждёт периодического обнаружения изменения SQLite. У Codex также есть собственный watcher внешних изменений очереди с интервалом десять секунд; он работает без вызовов модели. Поэтому не обещай отсутствие любых внутренних проверок на уровне процессов Codex.

Из исходников следует: занятому чату сообщение оставляют в очереди; пользовательское прерывание не должно автоматически отменяться очередью; добавление в очередь незагруженного чата не равно загрузке чата. Это исследованные ветви, а не выполненные нами живые тесты всех состояний.

Основные места исходников:

- [Выбор и разбор транспорта](https://github.com/openai/codex/blob/f021168bde5357009fceb0477835ad90bd54c17c/codex-rs/app-server-transport/src/transport/mod.rs).
- [Запуск listener и режим одного клиента](https://github.com/openai/codex/blob/f021168bde5357009fceb0477835ad90bd54c17c/codex-rs/app-server/src/lib.rs).
- [Обработчик RPC очереди](https://github.com/openai/codex/blob/f021168bde5357009fceb0477835ad90bd54c17c/codex-rs/app-server/src/request_processors/thread_queue_processor.rs).
- [Сохранение очереди и пробуждение](https://github.com/openai/codex/blob/f021168bde5357009fceb0477835ad90bd54c17c/codex-rs/ext/queue/src/service.rs).
- [Тест idle-доставки upstream](https://github.com/openai/codex/blob/f021168bde5357009fceb0477835ad90bd54c17c/codex-rs/app-server/tests/suite/v2/thread_queue.rs).
- [Официальное описание API](https://learn.chatgpt.com/docs/app-server).

Хуки Codex реагируют на события его собственного runtime. Они не предоставляют внешний RPC endpoint и не нужны для подтверждённой доставки. Внутренний Desktop IPC, включая `~/.codex/ipc/ipc.sock`, не является выбранным App Server API.

## 5. Подтверждённый живой тест

28 октября на macOS выполнена одна разрешённая пользователем отправка. Использован bundled Codex CLI `0.164.0-alpha.11.1` из установленного Desktop.

Последовательность и доказательства:

1. Предыдущий ответ агента завершился. Старый Desktop и его приватный App Server остановились.
2. Запущен один заменяющий общий App Server с loopback WebSocket listener. Desktop запущен с подключением к этому endpoint.
3. Проверено реальное TCP-соединение Desktop с общим сервером, отсутствие отдельного приватного сервера у нового Desktop и загрузка исходного чата. До отправки чат был `idle`.
4. Вспомогательный процесс `sleep` завершился; ожидание использовало блокирующий OS wait, без модели.
5. Настоящий Rust-клиент выполнил preflight и один `thread/queue/add`. Получен проверенный receipt, exit code клиента — 0.
6. В исходном чате начался новый ход. Отдельное чтение `thread/items/list` подтвердило тот же `clientUserMessageId` в пользовательском сообщении нового хода.
7. Команда проверки, запущенная уже агентом этого нового хода, оказалась дочерним процессом того же общего App Server. Desktop продолжал держать соединение с ним.
8. Агент автоматически ответил пользователю и записал результат в описание [PR #4](https://github.com/festy23/codex-awake/pull/4).

Временный наблюдатель сначала не распознал совпадение из-за обёртки ответа: в использованной версии нужное поле находится в `data[].item.clientId`. Этот диагностический дефект проверен отдельным запросом чтения и исправлен во временном helper. Повторная отправка события не выполнялась.

Подтверждены приём сообщения и запуск нового хода в неактивном загруженном чате. Receipt не доказывает завершение поручения. Тест не проверял production backend/effectum, устойчивость к падениям, exactly-once, busy/cold/interrupted состояния или произвольный чужой процесс. `sleep` был дочерним процессом helper; универсальный наблюдатель из этого теста не получен.

В отличие от прежнего эксперимента с дополнительным App Server и общим хранилищем, этот тест подтвердил прямую выбранную связку. Старый эксперимент не используй как доказательство прямого подключения.

## 6. Настройка Desktop и временные материалы

В исследованной установленной сборке найден выбор WebSocket endpoint через переменную `CODEX_APP_SERVER_WS_URL`. В тесте использовался URL формы `ws://127.0.0.1:<port>/rpc`. Порт выбирался для теста; фиксированного production-порта нет. Исходники Desktop и бинарник App Server не патчились.

Наличие этого механизма в одной сборке не означает стабильный публичный контракт запуска Desktop. Установка, совместимость версий, владение процессом сервера, безопасное переключение Desktop, восстановление и удаление такой настройки ещё требуют проектирования. Простой запуск второго сервера рядом с обычным Desktop не настраивает совместный доступ.

В окружении теста приложение находилось в `/Applications/ChatGPT.app`, а bundled CLI — в `/Applications/ChatGPT.app/Contents/Resources/codex-cli/bin/codex`. Не подменяй его произвольной системной версией CLI: версию бинарника и схему RPC проверяй отдельно от свежего `main` исходников. Схему установленной версии можно получить через `codex app-server generate-json-schema --experimental`, указав каталог вывода вне Git для временного исследования.

После теста Desktop оставлен подключённым к общему тестовому серверу. Это историческое состояние на момент передачи; не предполагай, что процессы или endpoint всё ещё существуют. Перед любыми действиями проверь текущий запуск. Не закрывай Desktop и не останавливай активные чаты автоматически ради проверки handoff.

При подготовке handoff инструменты Desktop `attach_artifact` и `open_in_codex` отсутствовали в доступном наборе инструментов агента. Пробуждение, RPC-чтение и выполнение команд ранее в этом режиме работали. Причина отсутствия этих инструментов не исследована; связь со сменой транспорта не установлена. В S3 отдельно проверь доступность Desktop app tools: успешная доставка не подтверждает полную совместимость всех функций Desktop.

Временные материалы на машине теста находятся в `/private/tmp/codex-awake-direct-live/`: `state.json`, `verification.json`, `controller.py`, `inspect.mjs`, `restore-default.py`, `pr.json`. Они могут исчезнуть и не являются артефактами установки. Сценарий восстановления разрешает обычный запуск Desktop только после проверки, что целевой чат idle.

Не запускай старый controller повторно и не переотправляй сохранённое тестовое сообщение. Runtime-данные, переписки, PID, фактические порты, логи и credentials не переносить в Git. Python/Node helpers были временным стендом; production backend остаётся Rust.

## 7. Реализованный код и состояние Git

На момент передачи:

| Объект | Состояние |
|---|---|
| `main` | `9c6f33b`; PR #1–3 слиты |
| [PR #4](https://github.com/festy23/codex-awake/pull/4) | Открытый draft, не слит; ветка `codex/direct-wake-live`, коммит `bc5b176` |

| Production backend и effectum | Отсутствуют; библиотека ещё не добавлена в Cargo-зависимости |

Перед продолжением обнови refs и проверь статус PR: эти значения — snapshot, а не инструкция вернуть репозиторий к старому коммиту. Не сливай PR #4 без отдельного одобрения пользователя. Новый handoff публикуется отдельной веткой от `main`, без включения изменений PR #4.

Код диагностики расположен в [prototypes/app-server-queue/](prototypes/app-server-queue/README.md). В PR #4 он поддерживает явный `--websocket-url`; существующий Unix-сокетный режим сохранён для диагностики. Production-транспорт выбран TCP WebSocket.

Алгоритм клиента: `initialize` → `initialized` → страницы `thread/loaded/list` → один `thread/queue/add` → проверка receipt → отключение. Клиент не запускает сервер, не загружает чат через `thread/resume`, не вызывает `turn/start`, не использует внутренний IPC и не повторяет отправку.

| Исход диагностики | Значение |
|---|---|
| `checked` | Загруженный адресат найден; отправки не было |
| `not_sent` | Отправка в очередь не начиналась |
| `accepted` | Receipt совпал по ID сообщения и содержимому |
| `rejected` | Получена предусмотренная прототипом ошибка протокола |
| `delivery_unknown` | Возможный приём не подтверждён; автоматический повтор запрещён |

Не переносить классификацию диагностического клиента в production как уже согласованный полный контракт ошибок.

Rust закреплён на `1.99.1`, edition 2024, rustfmt + Clippy. CI запускается на pull requests, на macOS. Перед публикацией WebSocket-прототипа прошли сборка, форматирование, строгий Clippy, 16 тестов, проверка локальных ссылок и `git diff --check`. Это выполненные проверки, не независимое ревью.

```sh

cargo clippy --manifest-path prototypes/app-server-queue/Cargo.toml --locked --all-targets --all-features -- -D warnings
```

## 8. Оставшиеся решения и порядок работы

Следующие шаги — рабочий порядок, а не готовый нормативный алгоритм. Перед изменением поведения закрой соответствующий контракт по `writing-spec` и согласуй недостающие наблюдаемые решения с пользователем.

1. **Сверить Git и документацию.** Учесть PR #4, сохранить посторонние изменения и работать в отдельной `codex/<task>`. В `main` не пушить. Не повторять уже выполненную пробу как первый шаг.
2. **Закрыть S3 для установки и доставки.** Определить способ настройки одного общего App Server для Desktop и backend, совместимые версии, endpoint, доступ, ограничения сообщения, таймауты, handshake, маппинг инструкции и события, receipt и поведение всех нужных состояний чата. Нужен управляемый жизненный цикл, а не постоянная зависимость от временного helper.
3. **Исследовать API выбранной версии effectum и закрыть S1/S2.** Определить границу прикладного состояния и внутренней SQLite effectum, реальные транзакционные возможности, миграции, фиксацию попытки, восстановление, повторы, timeout, параллелизм и сроки хранения. Не предполагать общую транзакцию регистрации и enqueue без проверки API библиотеки. Внутренними таблицами effectum управляет сама библиотека.
4. **Закрыть S4 для macOS.** Выбрать устойчивую идентичность экземпляра процесса и событийную подписку, обработать гонку регистрации с завершением, переиспользование PID и восстановление после пропущенного события. Обычный `waitpid` дочернего `sleep` не решает наблюдение произвольного уже запущенного процесса.
5. **Закрыть S5.** Определить внешний интерфейс регистрации/отмены, получение исходного чата и заранее разрешённой инструкции, валидацию и ошибки. Пользователь ещё не выбрал HTTP/gRPC API для нашего backend; не создавать их фиктивно.
6. **Реализовать сквозной сценарий по завершённым контрактам.** Сначала регистрация → наблюдение → устойчивое событие → доставка, затем согласованные восстановление и эксплуатация. Спецификации и поведение публиковать вместе. CI-интеграции и перенос на другие ОС — отдельные дальнейшие задачи.

Особое конкурентное окно: Codex может принять сообщение до падения backend или потери ответа. Повтор job в effectum не даёт права снова отправить сообщение. Различай доказанный неприём, подтверждённый приём и неопределённый исход; предусмотренные в спецификациях `dispatching`/`delivery_unknown` не заменяй обычной повторяемой ошибкой worker.

## 9. Дополнительный контекст исследования

У [Kandler3/agent-wake](https://github.com/Kandler3/agent-wake/tree/c017491cee4856d27a7eaa73e0bd35ca3ba8b29f) клиент читает порт уже настроенного общего сервера, подключается по WebSocket и отправляет `turn/start.toolOutput`. Сам репозиторий не предоставляет настройку Desktop для общего сервера. Не считай его готовым установщиком и не переноси его метод доставки: у нас утверждён `thread/queue/add`.

Локальные исследовательские копии могут сохраняться в `/private/tmp/codex-awake-source`, `/private/tmp/codex-awake-upstream` и `/private/tmp/codex-awake-essay-reference`. Для нового окружения используй закреплённые публичные ссылки, а не наличие этих временных каталогов.

Для формальных спецификаций обязателен [writing-spec](https://github.com/photorus/essay-platform/blob/9dc96179ab36d36eb05a45e16d120f625402c42a/.agents/skills/writing-spec/SKILL.md). В `docs/` допускается только `modules/`. Исследования, результаты проб и этот handoff не переносить в нормативные алгоритмы. Неполные контракты S1–S5 остаются явно неполными до определения недостающего поведения.
