# Codex Awake: исследование и проект первой версии

Дата: 2026-10-25. Статус: исследование завершено в части upstream; транспорт Desktop требует сквозной проверки.

Итоговое решение от 2026-10-26: [собственный Rust Backend + NATS JetStream](rust-jetstream-design.md). Предложения о переносе Node.js-ядра ниже сохранены как история исследования и не являются текущим планом. Pueue также исключён.

Обновление 2026-10-26: [исследование официального исходного кода Codex](codex-source-findings.md) подтвердило нативный `turn/start.toolOutput`, автоматический idle-dispatch очереди и ограничения MCP Events. Прежние предположения о необходимости отдельного backend и неопределённости самого `toolOutput` уточнены там. Сквозное пробуждение установленного Desktop по-прежнему не тестировалось.

## Цель

Фоновый процесс заканчивается → сохраняется событие → возобновляется исходный чат Codex Desktop с его прежними инструкциями. Пока процесс работает, модель не вызывается. Ожидание не реализуется автоматизацией, которая периодически спрашивает модель о статусе.

Первая версия рассчитана на открытый Desktop и включённый компьютер. Пробуждение агента не означает вывод ноутбука из сна. После перезапуска приложения возможность доставки зависит от транспорта; восстановление запущенных процессов после перезагрузки ОС в первую версию не входит.

## Что уже сделано коллегой

Источник: https://github.com/Kandler3/agent-wake

Изучен commit `c017491cee4856d27a7eaa73e0bd35ca3ba8b29f`.

- CLI и worker на Node.js без npm-зависимостей; `run`, `emit`, `status`, `jobs`, `cancel`, `deliver`, `doctor`.
- Worker отделяется от запускающего процесса, сохраняет код завершения, ограниченные логи и хвост вывода.
- UUID предотвращает повторную регистрацию той же команды; блокировки ограничивают повторное исполнение и доставку.
- Событие отправляется в загруженный исходный чат через `turn/start.toolOutput`.
- При потере подтверждения состояние становится `delivery_unknown`; автоматическая повторная доставка прекращается.
- Есть скилл, Windows-установщик и временный индикатор ожидания в названии чата.

На данном Mac выполнены исходные тесты: 19 passed, 1 skipped (Windows installation), 0 failed. Они используют имитацию App Server и реальные локальные процессы; это НЕ доказательство пробуждения Desktop.

## Ограничения исходника

1. Требует УЖЕ существующего общего App Server с WebSocket на localhost. Установщик его не создаёт и Desktop к нему не подключает.
2. `doctor` проверяет связь и наличие загруженного чата, но не поддержку `turn/start.toolOutput`.
3. `toolOutput` — интеграционный путь, поддержка которого не гарантирована одним лишь наличием стандартного App Server API.
4. При ожидании процесса каждые 200 мс читается файл отмены; модель в этом не участвует. Повторная доставка при недоступном сервере тоже использует локальные таймеры.
5. На POSIX отмена убивает только непосредственный дочерний процесс. Внуки могут продолжить работу и удерживать stdout/stderr открытыми.
6. `emit` — локальная команда, а не HTTP webhook. Пример `gh run watch` опрашивает CI средствами gh: экономит токены, но не является push-интеграцией CI.
7. Не гарантирует exactly-once и не восстанавливает выполнение команды после перезапуска ОС.

## Наблюдения о текущей установке

- Desktop использует свой bundled Codex CLI; CLI в PATH имеет другую версию.
- Текущий App Server запущен как дочерний stdio-процесс Desktop.
- Стандартный Unix control socket общего daemon не найден. Следовательно, нельзя просто заменить Windows launcher на shell-скрипт и заявить готовность.
- `codex queue` существует и официально документирован. Он вызывает `thread/queue/add` через выбранный App Server; наличие команды само по себе не доказывает пробуждение чата текущего Desktop.
- В установленном Desktop есть маршрут `codex://threads/wake/<UUID>`, который проверяет очередь и вызывает resume. Это внутренняя деталь конкретной сборки, не обещание совместимости.
- Прямое подключение обычного Node-клиента к app-tools pipe закрывается без ответа. Проверка через штатный launcher установленного MCP-плагина тоже вернула `Codex app tools pipe closed`. Этот путь не считаем доступным и не обходим проверку клиента.

Личные ID чатов, конфигурации, содержимое переписок и секреты в проект не копируются.

## Варианты

### A. Порт agent-wake + существующий общий App Server

Самый близкий к исходнику вариант. Переносим установку и управление процессами, проверяем поддержку доставки на реальном сервере. Для нашего Desktop остаётся отдельная задача настройки общего сервера. Она может потребовать перезапуска приложения и не должна скрываться за успешными unit-тестами.

### B. Порт agent-wake + штатная очередь Codex

Предпочтительный кандидат, если сквозная проверка подтвердит доставку в текущий Desktop. Событие передаётся через `codex queue` или соответствующий API. Не запускаем отдельный inference runtime и не подменяем настройки безопасности чата. Транспорт очереди доставляет текстовый follow-up, поэтому сообщение явно отделяет заранее заданную инструкцию от недоверенного результата процесса.

Нельзя автоматически объявлять доставку успешной только по коду 0: нужны ID/подтверждение очереди и затем наблюдаемое продолжение именно исходного чата. Неоднозначное завершение отправки блокирует автоматическое воспроизведение.

### C. MCP Events / Work Cloud

Официальный webhook-механизм подписок. Подходит для дальнейшего браузерного варианта, но меняет среду выполнения. Официальная документация указывает Work на web, Work Desktop с выбранным Cloud и dots. Поддержку локального Codex из этого выводить нельзя.

## Предлагаемые изменения после согласования

1. Сохранить upstream Node.js-ядро и MIT attribution.
2. Добавить Unix-установщик/launcher с проверкой Node 22+, сохранением настроек и защитой от перезаписи чужих файлов.
3. Выделить транспорт доставки. Не выбирать случайный порт, чат или другой сервер в качестве fallback.
4. Заменить 200-мс опрос отмены на `fs.watch` каталога задания плюс проверку после подписки, закрывающую гонку; дедлайн — один таймер.
5. На POSIX запускать команду в своей process group и отменять всю эту группу. На Windows сохранить `taskkill /T`.
6. Добавить сохранённую инструкцию продолжения, если она нужна помимо контекста чата. Результаты команды остаются недоверенными данными.
7. Скилл: зарегистрировать задачу, сохранить receipt, завершить ход; после события проверить результат и выполнять только ранее разрешённое продолжение. Для цикла исправлений явно задавать предел попыток и условие остановки.
8. Матрица CI: macOS, Linux, Windows × Node 22/24. Локальный успешный прогон не выдаётся за успешный прогон всей матрицы.

Внешний CI без опроса требует webhook либо собственного push/stream API. Универсальный интерфейс события можно подготовить сейчас; реальные TeamCity/Arcadia/GitHub интеграции требуют выбора конкретного источника и канала доставки до локального компьютера. Локальный HTTP listener сам по себе недоступен удалённому CI.

## Приёмка

- Успех, ошибка запуска, ненулевой exit code, timeout и отмена дают корректный durable receipt.
- Отмена/timeout не оставляют обычных дочерних процессов в принадлежащей заданию POSIX-группе.
- При обычном ожидании нет повторных status-запросов или inference-вызовов.
- Дубликат job ID не запускает команду второй раз; неопределённая доставка не повторяется автоматически.
- Установщик повторяем и сохраняет пользовательские данные.
- Отдельный сквозной тест: разрешённая безвредная команда завершилась ПОСЛЕ окончания хода агента; исходный чат самостоятельно продолжил работу, прочитал результат и создал проверяемый локальный маркер. До этого пункта формулировка результата — «порт протестирован», а не «Desktop wake работает».
