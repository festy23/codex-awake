# Восстановление состояния

Статус: неполный контракт; S1, S2 и S4.

## Описание

Продолжить сохранённые ожидания и обработку событий после перезапуска backend.

## Запуск

Запуск backend после открытия прежнего хранилища SQLite. Не создавать пустое хранилище вместо недоступного существующего.

## Входные параметры

Внешний payload отсутствует. Конфигурацию хранения определить в [settings](../settings.md).

## Результат

Восстановленные наблюдения и доставки либо зафиксированные состояния, требующие разбора. Не запускать наблюдаемые команды повторно.

## Ресурсы

- [Регистрации и доставки](../database/state.md).
- [Очередь задач](../queue/events.md) и [worker effectum](../queue/worker.md).
- [Идентификация процесса](../../process-watch/operations/attach-process.md).

## Алгоритм работы

Полный алгоритм перечисления записей, блокировки экземпляра и условных обновлений приостановлен до S1, S2 и S4.

1. Исключить конкуренцию нового экземпляра backend со старым перед классификацией незавершённых отправок; механизм владения определить в S1.
2. Оставшиеся попытки `dispatching`, чей результат не зафиксирован, считать `delivery_unknown`. Это правило действует даже если запрос фактически не успел уйти.
3. Для `accepted` исключить новую отправку при повторной выдаче события.
4. Для действующих наблюдений проверить идентичность экземпляра процесса, а не только совпадение PID. Не подключаться к процессу, переиспользовавшему PID.
5. При отсутствии прежнего процесса применить отдельно определённую политику потерянного наблюдения S4. Не объявлять восстановленным событие ОС, которое служба не наблюдала.
6. Возобновить только безопасные повторы через effectum с выбранной в S2 политикой. При запуске worker исключить отправку до проверки восстановленного прикладного состояния. Не вызывать модель во время восстановления.
