# Backend

Статус: проект.

Backend координирует ожидания и доставку. Предлагается один Rust-бинарник с режимом службы и CLI; Tokio и async-nats — кандидаты библиотек, версии пока не закреплены.

## Операции интерфейса

| Операция | Вход | Результат |
|---|---|---|
| Зарегистрировать ожидание | Ключ идемпотентности, источник и точный запуск, целевой чат, продолжение | ID устойчиво сохранённого ожидания либо ошибка |
| Получить статус | ID ожидания | Состояние наблюдения и доставки, последняя диагностическая причина |
| Отменить ожидание | ID ожидания | Подтверждение отмены либо указание, что отправка уже началась |
| Диагностика | Локальная конфигурация | Доступность брокера, службы и транспорта; без запуска модели |
| Разобрать спорную доставку | ID доставки и решение оператора | Результат сверки либо явно запрошенный повтор с риском дубля |

Это логические операции, не готовый CLI-синтаксис. Коды ошибок, wire format и способ IPC относятся к D4. Один ключ регистрации с теми же полями возвращает существующее ожидание; с другим содержимым должен давать конфликт, а не незаметно менять чат.

## Зависимости и ограничения

Backend использует [схему состояния](data.md), [адаптеры источников](../sources/README.md) и [транспорт Codex](../codex-delivery/README.md). Не содержит своего inference runtime и не открывает чужие базы Desktop для прямой записи.

Переходы и порядок внешних эффектов описаны в [жизненном цикле](lifecycle.md). Служба должна иметь единственного активного владельца доставки на локальную установку; конкретный механизм исключения второго экземпляра входит в инфраструктурную спецификацию перед реализацией.
