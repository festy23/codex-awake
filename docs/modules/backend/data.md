# Данные и очередь

Статус: проект логической модели. Имена ресурсов, сериализация и физические настройки ещё не утверждены; это не готовая схема для создания stream.

## Сущности

| Сущность | Необходимые поля | Назначение |
|---|---|---|
| Wait | `wait_id`, ключ регистрации, `source`, `run_id`, `thread_id`, continuation, статус, timestamps | Связь конкретного запуска с разрешённым продолжением |
| SourceEvent | версия схемы, `event_id`, источник, `run_id`, финальный статус, время, ограниченный результат/ссылки | Факт завершения одной попытки запуска |
| Delivery | `delivery_id`, `wait_id`, `event_id`, состояние, номер попытки, ошибка, receipt | Доставка результата одному ожиданию |
| SourceCursor | источник/подписка, позиция | Возобновление чтения, если источник поддерживает replay |

`event_id` стабилен для повтора одного результата; повторный запуск CI имеет другой идентификатор. Одно событие может соответствовать нескольким ожиданиям: `delivery_id` различает такие доставки. При сериализации нужны явные типы, обязательность, ограничения размера и версия миграции — D3.

## Предлагаемое размещение

- JetStream KV хранит регистрации и состояния доставки.
- Stream хранит результаты источников; durable consumer выдаёт их обработчику с explicit ack.
- Для события с несколькими получателями обработчик фиксирует состав доставок. Подтверждение события допустимо после устойчивого решения по каждой доставке; незавершённые попытки требуют механизма возобновления.
- Неоднозначность и исчерпание повторов сохраняются в состоянии для разбора. Нельзя полагаться только на достижение MaxDeliver у consumer как на обработку ошибки.

Детали fan-out и сканирования при восстановлении входят в D3. KV, stream и Codex не образуют общей транзакции; схема должна явно закрыть разрывы между ними.

## Устойчивость и лимиты

File storage, durable consumer и ack — необходимые части проекта, но не гарантия сохранения любого подтверждённого сообщения при отключении питания. Политика fsync зависит от версии и конфигурации. См. [документацию NATS о потере узла](https://docs.nats.io/learn/jetstream/surviving-node-loss).

Для необработанных сообщений нельзя выбирать незаметное вытеснение при заполнении. Проектный вариант — отклонение новой публикации с видимой ошибкой и восстановлением от источника. Время хранения, лимит диска, окно дедупликации и срок хранения завершённых записей должны быть определены до реализации. Broker deduplication не заменяет журнал доставки в Codex.
