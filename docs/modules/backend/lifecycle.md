# Жизненный цикл ожидания и доставки

Статус: проект алгоритма. Физические ключи, concurrency и retry-параметры уточняются в D3–D5.

## Регистрация и получение результата

1. Проверить наличие конкретного источника, запуска, чата и разрешённого продолжения.
2. Сохранить регистрацию идемпотентно. Не отвечать об успехе до подтверждения хранения.
3. Активировать наблюдение за указанным запуском. После рестарта восстановить наблюдение из записи, не повторяя запуск задачи.
4. Сформировать стабильный `event_id`, опубликовать результат и дождаться PubAck. До этого не считать результат переданным брокеру.
5. Сохранить прогресс источника после публикации. Если служба упала между этими действиями, повторное чтение может повторно опубликовать тот же результат.

## Отправка в Codex

1. Найти ожидание и запись доставки. Уже принятые доставки повторно не отправлять. Отменённые до начала отправки подавить.
2. Для новой или безопасно повторяемой доставки устойчиво записать `dispatching` до внешнего вызова. Конкурирующий обработчик не должен получить право второй отправки.
3. Вызвать транспорт один раз для этой попытки с точным чатом и ограниченным результатом.
4. При подтверждённом приёме сохранить `accepted` и receipt. Это не статус завершения работы модели.
5. При доказанном неприёме и временной ошибке сохранить `retry_wait`; при постоянной ошибке или исчерпании лимита — `needs_attention`.
6. При возможном приёме без подтверждения сохранить `delivery_unknown`. Автоматически не отправлять заново.
7. Подтверждать сообщение брокеру после записи состояния. Для `retry_wait` ack допустим только при наличии устойчивого механизма последующего запуска; иначе сообщение остаётся неподтверждённым. Конкретную стратегию выбираем в D3–D5, не смешиваем два независимых планировщика повторов.

## Окна падения

| Момент | Действие при восстановлении |
|---|---|
| До сохранения регистрации | Клиент повторяет регистрацию с тем же ключом |
| После регистрации, до подписки | Возобновить наблюдение |
| После публикации, до сохранения позиции источника | Допустить повтор события; сверить delivery state |
| После записи `dispatching`, до сохранённого результата | `delivery_unknown`, даже если запрос фактически ещё не ушёл |
| После `accepted`, до ack | Повторная выдача подтверждается без новой отправки |
| После безопасной ошибки | Продолжить по устойчиво сохранённой политике повторов |

Сбой брокера во время записи ответа Codex также оставляет неоднозначность. Нельзя признать попытку безопасной только потому, что локальная запись не удалась.

## Отмена и перезапуск

Отмена, выигравшая гонку до перехода в `dispatching`, подавляет отправку. После этого перехода гарантировать отмену уже нельзя: показать отправку в процессе или её результат. Отмена ожидания не отменяет CI и не отзывает принятое сообщение.

При рестарте служба сверяет регистрации, события и доставки. Старые `dispatching` сначала классифицируются как неизвестные; повтор запрещён до доказательства неприёма либо явного решения оператора. Намеренная остановка пользователем не должна трактоваться как разрешение продолжить работу агента.
