# Отправка результата

Статус: неполный контракт; S3. Метод `thread/queue/add` и прямой вызов сервера исходного чата утверждены пользователем 2026-10-27. Локальный TCP WebSocket на loopback-адресе утверждён 2026-10-28. Способ настройки общего endpoint Desktop, совместимые версии, маппинг сообщения, таймауты и поведение жизненного цикла ещё не определены. Контракт не считать готовым к реализации production-доставки.

## Метод

Внутренняя операция `codex-delivery` вызывает Codex App Server JSON-RPC `thread/queue/add` через локальный TCP WebSocket на loopback-адресе. Передавать идентификатор исходного чата в `params.threadId`, сообщение в `params.input`, идентификатор сообщения в `params.clientUserMessageId`. Не использовать `turn/start` как резервный способ доставки.

## Описание

Передать уведомление о завершении процесса в исходный чат и вернуть результат приёма.

## Ресурсы

Общий endpoint App Server, обслуживающего нужный чат Desktop. Не запускать дополнительный App Server для записи в общее хранилище очереди. Не использовать внутренний IPC Desktop вместо выбранного RPC. Не писать напрямую в базу очереди Codex.

## Входные параметры

| Название | Тип | Обязательность | Описание |
|---|---|---|---|
| `delivery_id` | Строка | Да | Корреляция попытки; не предполагает поддержку идемпотентности получателем |
| `thread_id` | Строка | Да | Исходный чат |
| `continuation` | Строка | Да | Заранее разрешённая инструкция |
| Событие завершения | Структура по контракту backend | Да | [Факт завершения процесса](../../backend/queue/events.md) |

## Выходные параметры

Ответ должен различать подтверждённую постановку в очередь, доказанный неприём и неизвестный исход. Источник receipt — `result.queuedSubmission` ответа `thread/queue/add`; он содержит `id`, `clientUserMessageId` и `input`. Правила проверки receipt, его представление во внутреннем ответе и классификацию конкретных ошибок определить в S3. Не считать `clientUserMessageId` обещанием дедупликации получателем.

## Результат в случае успеха

Подтверждена постановка сообщения в очередь указанного чата. Не заявлять запуск или завершение работы агента на основании этого ответа.

## Результат в случае ошибки

Потерю ответа после возможного приёма классифицировать как неизвестный исход, а не доказанный неприём. Не менять адресата и не выполнять скрытую повторную отправку.

## Алгоритм работы

Полный алгоритм внешнего вызова приостановлен до S3: определить общий endpoint, маппинг `continuation` и события в `input`, правило формирования `clientUserMessageId`, timeout, проверку ответа и поведение для busy/cold/interrupted чатов.

Для выбранного транспорта соблюдать следующие ограничения:

1. Использовать только переданный `thread_id`.
2. Отделять данные события от инструкции `continuation`; данные не расширяют разрешённые действия пользователя.
3. Выполнить одну попытку передачи в рамках вызова операции. Политику автоматических повторов передать backend.
4. Подтверждённый приём вернуть с receipt; возможный приём без подтверждения вернуть как неизвестный исход.
5. Доказанный неприём вернуть с причиной, позволяющей backend различить постоянную и временную ошибку. Классификацию для конкретного транспорта определить до реализации.

Не считать код завершения CLI достаточным подтверждением без установленного контракта команды. Не писать напрямую в внутреннюю базу Desktop.

## Ошибки

Для выбранного транспорта определить коды, статусы и message для недоступного сервера, недоступного чата, отказа в доступе, несовместимой версии, превышения размера и неопределённого результата. Не назначать эти коды до выбора интерфейса.
