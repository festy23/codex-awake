# Доставка в Codex Desktop

Статус: проект. Доступ к App Server именно установленного Desktop и сквозной wake ещё не подтверждены.

## Граница модуля

Вход: `delivery_id`, точный `thread_id`, разрешённое продолжение и отдельно данные результата. Выход: подтверждённый приём с receipt, доказанный неприём либо неизвестный исход. Транспорт не выбирает другой чат при ошибке адресации и не запускает отдельного агента вместо Desktop незаметно для пользователя.

## Кандидаты транспорта

| Кандидат | Что установлено исследованием | Что ещё проверить |
|---|---|---|
| `codex queue` / `thread/queue/add` | Очередь и обработка idle-чата есть в исследованном исходнике | Адресация Desktop, loaded/cold/busy/interrupted состояния, receipt и возможность сверки |
| `turn/start.toolOutput` | В исследованном App Server результат может запустить ход или попасть в активный | Доступный общий сервер, совместимость Desktop, семантика активного хода |

Источники и версии: [исследование Codex](../../research/codex-source-findings.md). Наличие API в исходнике и успешный вызов отдельного App Server не доказывают работу с чатом Desktop. Внутренние deep links и прямая запись в базу Desktop не выбираются как стабильный публичный контракт.

## Подтверждение и неопределённость

Код завершения CLI сам по себе недостаточен: адаптер должен знать, какое подтверждение приёма предоставляет выбранная команда. Если подтверждение не различает сохранение и запуск, это различие должно сохраняться в статусе продукта.

Потеря соединения после возможной передачи даёт `delivery_unknown`. Exactly-once возможен только при достаточном идемпотентном контракте получателя; ни JetStream, ни локальная запись сами его не создают. Возможность сверить приём по `delivery_id` надо доказать, а не предположить.

## Проверка совместимости

Зафиксировать версию Desktop и используемого CLI, путь к серверу и его владельца. В отдельном разрешённом тестовом чате завершить исходный ход, доставить безвредный результат и проверить автоматическое продолжение того же чата. Отдельно проверить занятый чат, остановку пользователем и незагруженный чат.

Проверка доступности не должна сама запускать модель. Сырые логи не передаются как авторитетная пользовательская инструкция. Готовый формат сообщения и лимиты выбираются после проверки транспорта.
