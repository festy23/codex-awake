# Структура репозитория

Статус: проект. Сейчас существуют `AGENTS.md`, `README.md` и `docs/`. Дерево ниже описывает будущие пути и не означает, что код уже написан.

```text
codex-awake/
├── AGENTS.md
├── README.md
├── docs/
│   ├── index.md
│   ├── architecture/          # обзор и открытые решения
│   ├── modules/               # прикладные контракты
│   ├── infra/specification/   # локальное размещение и эксплуатация
│   ├── adr/                   # принятые решения
│   ├── development/           # структура и проверка
│   ├── runbooks/              # диагностика и восстановление
│   ├── standards/             # правила документации
│   └── research/              # источники и исторические варианты
├── Cargo.toml                # будущий один пакет, CLI + служба
├── Cargo.lock                # фиксируется для бинарного приложения
├── src/
│   ├── main.rs               # выбор режима запуска
│   ├── cli/                  # команды и вывод статуса
│   ├── domain/               # сущности и переходы состояния
│   ├── service/              # координация и восстановление
│   ├── storage/              # JetStream и KV
│   ├── sources/              # CI и локальные задачи
│   ├── codex/                # транспорт Desktop
│   └── platform/             # пути и управление процессами
├── tests/                    # интеграционные и аварийные сценарии
├── packaging/                # установка по платформам
└── skills/                   # будущий пользовательский скилл регистрации
```

Начинаем с одного Cargo package. Выделять workspace crates следует при реальной необходимости отдельного API или поставки. `domain` не зависит от NATS, Desktop API и платформы; координация связывает адаптеры. Сетевые DTO не должны становиться доменной моделью автоматически.

Файлы в `packaging/`, `skills/` и `src/` создаются при соответствующей реализации. Пустые заглушки не считаются выполненным модулем. Конфигурационные примеры добавляются только после выбора поддерживаемых параметров и их значений.
