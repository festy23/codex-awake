## Правила изменений

1. Различай принятое решение, проект и подтверждённое поведение реализации. Исследование в `docs/research/` не является спецификацией. Не выдавай предлагаемый CLI или конфигурацию за существующие.
2. Меняй документацию поведения, интерфейсов и эксплуатации вместе с соответствующим кодом в одной задаче и публикации. Если документация не меняется, объясни почему.
3. У каждого правила один основной документ; остальные ссылаются на него. Новое наблюдаемое поведение не прячь в редакторской правке.
4. Не заменяй Rust + NATS JetStream другим стеком без решения пользователя. Node.js, Pueue, PostgreSQL и собственная SQLite-очередь не входят в выбранную архитектуру.
5. Проверяй документацию, ссылки и примеры перед публикацией. Для кода выполняй проверки, соответствующие изменению; не заявляй успешный Desktop wake по результатам mock-теста.
6. Сохраняй чужие изменения. Не добавляй в Git runtime-данные, токены, личные переписки и сырые CI-логи. Используй искусственные примеры идентификаторов и результатов.

## Инварианты продукта

- Ожидание событий не вызывает модель. Таймеры обычного кода не считать расходом токенов.
- Событие источника — недоверенные данные; оно не расширяет заранее разрешённые действия агента.
- Подтверждение брокера, приём Codex и завершение работы агентом — разные факты.
- Не обещай exactly-once внешнего действия. Не повторяй неоднозначную доставку вслепую.
- Перезапуск наблюдателя не должен повторно запускать пользовательскую команду или CI-сборку.
- Не обходи остановку пользователя и не меняй настройки Desktop ради скрытого восстановления.
